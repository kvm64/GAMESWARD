# Технологические решения GAMESWARD

Этот документ объясняет, **почему** в GAMESWARD выбраны те или иные технологии. 
Он предназначен **для тех пользователей и разработчиков**, которые хотят понять 
логику архитектурных решений.

---

## 1. Django REST Framework (DRF) для API

### Что это

**Django REST Framework (DRF)** — это библиотека для Django, которая позволяет создавать RESTful API. Она предоставляет:
- **Сериализаторы** — преобразование моделей Django в JSON и обратно.
- **View-функции и ViewSet'ы** — обработка HTTP-запросов.
- **Аутентификацию** — токены, сессии, JWT.
- **Права доступа** — гибкая система permissions.
- **Пагинацию** — автоматическая разбивка на страницы.

### Почему DRF, а не альтернативы

| Альтернатива | Почему не выбрана |
| :--- | :--- |
| **Чистый Django (JsonResponse)** | Слишком много ручной работы: нужно вручную преобразовывать модели в JSON, обрабатывать ошибки, проверять права. DRF делает это автоматически. |
| **FastAPI** | Отличный фреймворк, но требует отдельного сервера и не интегрируется с Django-админкой. Для GAMESWARD важна единая экосистема. |
| **Django Ninja** | Более молодой, менее документированный. DRF — стандарт де-факто в Django-сообществе. |
| **GraphQL (Graphene)** | Избыточен для наших задач. REST проще для понимания студентами. |

### Что это даёт GAMESWARD

1. **Единый API для всех игр** — неважно, шахматы это или крестики-нолики, API одинаковый.
2. **Автоматическая документация** — DRF генерирует browsable API, который можно смотреть в браузере.
3. **Готовая аутентификация** — не нужно писать с нуля.
4. **Стандарт индустрии** — знание DRF пригодится студентам на работе.

## 2. Модульная архитектура игровых движков

### Что это

Каждая игра реализует **общий интерфейс** `GameEngine`:
- `get_initial_state()` — начальное состояние.
- `validate_move()` — проверка хода.
- `apply_move()` — применение хода.
- `check_game_over()` — проверка окончания.

### Почему это, а не монолит

| Подход | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Монолит** (вся логика в одном файле) | Просто для одной игры | Нельзя добавить вторую игру без переписывания |
| **Модульная архитектура** | Легко добавлять новые игры | Требует понимания абстракций |

### Что это даёт GAMESWARD

1. **Универсальность** — можно добавить любую игру, реализовав интерфейс.
2. **Изоляция** — каждая игра в своём файле, не мешает другим.
3. **Тестируемость** — каждую игру можно тестировать отдельно.

## 3. Фабрика игровых движков

### Что это

`GameEngineFactory` возвращает нужный движок по типу игры:
```python
engine = GameEngineFactory.get_engine('tictactoe')
```



### Почему это, а не прямые импорты

| Подход                                                       | Плюсы                   | Минусы                             |
| :----------------------------------------------------------- | :---------------------- | :--------------------------------- |
| **Прямые импорты** (`from services.games.tictactoe import TicTacToeEngine`) | Просто                  | Жёсткая привязка к конкретной игре |
| **Фабрика**                                                  | Гибкость, расширяемость | Требует понимания паттерна         |

### Что это даёт GAMESWARD

1. **Динамический выбор** — тип игры может приходить из базы данных.
2. **Расширяемость** — можно зарегистрировать новый движок без изменения кода API.
3. **Единая точка входа** — все игры получаются через фабрику.

## 4. Разделение ядра и игровых модулей

### Что это

- **Ядро** (`apps/accounts`, `apps/games`) — пользователи, роли, комнаты, сессии.
- **Игровые модули** (`services/games/`) — конкретные игры.

### Почему это, а не всё в одном

| Подход          | Плюсы                          | Минусы                |
| :-------------- | :----------------------------- | :-------------------- |
| **Всё в одном** | Просто для маленького проекта  | Сложно масштабировать |
| **Разделение**  | Модульность, переиспользование | Требует дисциплины    |

### Что это даёт GAMESWARD

1. **Разработчик с одной игрой** — берёт ядро + свой модуль, не трогает остальное.
2. **Разработчик с несколькими играми** — использует фабрику.
3. **Разработчик проектов с расширенными возможностями** — расширяете ядро, не ломая игровые модули.

## 5. SQLite для разработки

### Что это

**SQLite** — встроенная база данных, не требующая отдельного сервера.

### Почему SQLite, а не PostgreSQL

| Критерий           | SQLite      | PostgreSQL     |
| :----------------- | :---------- | :------------- |
| **Установка**      | Не требует  | Требует сервер |
| **Для разработки** | Идеально    | Избыточно      |
| **Для продакшена** | Не подходит | Рекомендуется  |
| **Для студентов**  | Просто      | Сложнее        |

### Что это даёт GAMESWARD

1. **Быстрый старт** — студент клонирует проект и сразу запускает.
2. **Нет зависимостей** — не нужно устанавливать PostgreSQL.
3. **Легко перейти** — в продакшене меняем `DATABASES` в `settings.py`.

------

## 6. Unfold для админки

### Что это

**Unfold** — современная тема для Django-админки.

### Почему Unfold, а не стандартная админка

| Критерий          | Стандартная админка | Unfold      |
| :---------------- | :------------------ | :---------- |
| **Внешний вид**   | Устаревший          | Современный |
| **Тёмная тема**   | Нет                 | Есть        |
| **Кастомизация**  | Ограниченная        | Гибкая      |
| **Для студентов** | Скучно              | Интересно   |

### Что это даёт GAMESWARD

1. **Визуальная привлекательность** — разработчик видит современный интерфейс.
2. **Тёмная тема** — удобно для глаз.
3. **Фирменные цвета** — можно настроить под конкретный проект.

------

## Итог

Все технологические решения GAMESWARD направлены на:

1. **Простоту для студентов** — минимум зависимостей, быстрый старт.
2. **Расширяемость** — легко добавить новую игру.
3. **Соответствие индустрии** — DRF, модульность, разделение ядра и модулей.
4. **Документированность** — каждое решение объяснено.
